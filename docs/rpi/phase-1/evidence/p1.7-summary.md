# P1.7: quota protection for public endpoints: evidence (2026-11-27)

Plan: [`../plan.md`](../plan.md) § P1.7 (AC-7.1 to AC-7.4). Critical tier (request handling in `arbiter/src`). Local only: nothing was written to Cloudflare. The dry runs build but don't upload.

## Research

- **Workers rate-limiting binding** (https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/, dateModified 2026-11-12):
  - Config: `[[ratelimits]] name, namespace_id, simple = { limit, period }`. `period` "Must be either `10` or `60`". `namespace_id` is a positive integer we choose. Counters are shared within a namespace across Workers in the account.
  - `limit({ key, delta })` returns `{ success }`.
  - "Rate limits are approximate and apply separately in each Cloudflare location", and "Counts are eventually consistent".
  - The page advises against IP keys, because IPs "can be shared by many users".
- **Free-plan availability: not stated anywhere.** I checked three pages, and none of them says whether the binding is on the Free plan or costs anything:
  - the binding page;
  - the Workers pricing page (dateModified 2026-11-18), which never mentions it;
  - the GA changelog, 2025-09-19 ("now stable and recommended for all production workloads", nothing on plans).
  
  This stays an **open item for the owner** (below).
- **Checked locally with wrangler 4.166.0:**
  - The binding works under `wrangler dev`: `limit 3` allowed 3, then refused, and a second key was unaffected. `delta` behaves as documented.
  - `[env.X].ratelimits` is read per environment, so each environment declares its own.
- **D1 Free** (limits page dateModified 2026-11-20, pricing page 2026-10-30):
  - "5 million / day" rows read, "100,000 / day" rows written.
  - "50 (Free)" queries per Worker invocation.
  - Past the daily limits, "D1 API will return errors", until "00:00 UTC".
- **Workers Free** (limits page dateModified 2026-11-25): "100,000/day" requests, "10 ms" CPU, and past the daily limit "Cloudflare returns **Error 1027**", until midnight UTC.
- **Ruled out:**
  - A limiter kept in D1 or KV would spend the D1 100k rows-written or KV 1k writes-per-day quota on every request it guards.
  - WAF rate-limiting rules need a zone; the arbiter runs on workers.dev.

## Red first

- `p1.7-red-tests.txt` (exit 1): 18 of 32 fail.
  - No 429 at all, and no `rate_limited_ip`.
  - `/v1/catalog` returned all 10,000 listings, and `/v1/audit/verify` was public.
  - The query plans show **unbounded scans the code already had**: one mandate's audit trail and the resolve guard (`NOT EXISTS … events WHERE mandate_id = ?`) scanned the whole chain, and `negotiate` scanned every listing for its sku.
- `p1.7-red-batch-writes.txt` (exit 1): a JSON-RPC batch with two `negotiate` calls was accepted. One `negotiate` costs up to 15 statements, and D1 Free allows 50 queries per invocation, so a 20-call batch would fail part-way through as `500 internal`.

Mistakes in my own tests, found and fixed during the red runs:
- An over-strict scan rule flagged the O(1) chain-head read, `ORDER BY seq DESC LIMIT 1`.
- A first "other routes" drive failed before it reached `negotiate`.
- A `ReadableStream` probe pulled at construction, so it reported a body read that never happened.
- The `/health` cache test and the redaction drives now run into the per-IP limit, so they set a high limit explicitly. Redaction then drops it to reach the 429 path and checks it for leaks too.

## What changed

- **`arbiter/src/quota.js`:** a per-IP limit on every request except CORS preflight, checked **before any body or database read**.
  - **Layer 1** is a fixed 60 s window per Worker instance: always on, no quota cost, at most 10,000 keys.
  - **Layer 2** is the `IP_RATE_LIMIT` binding, used where it is bound. A binding that throws is logged (`rate_limit: "binding_error"`) and skipped; the instance window still applies.
  - **Over the limit:** `429 rate_limited_ip`, with `retry-after: 60` (exposed to browsers through CORS). The log `reason` is `ip_limit_instance` or `ip_limit_binding`.
  - **Key:** `ip:` plus the salted IP hash, never the IP itself.
  - **Limits:** 100 per 60 s in staging and production, 1000 locally, where every script shares one loopback IP. The `IP_LIMIT_PER_60S` var and the binding must agree, and a test checks they do.
- **Caller identity:** in staging and production, only `cf-connecting-ip` identifies the caller. Before this change, a request without it fell back to `x-forwarded-for`, which a client can rotate. Anti-probing uses the same key (`buyerKey` now calls `ipHash`).
- **MCP batches:** at most 20 messages, each counted against the limit, and at most one `negotiate` or `accept_offer` call. Otherwise the batch is `400 invalid`.
- **`migrations/0002_read_indexes.sql`** (expand only, M2-compatible) adds two indexes:
  - `events_by_mandate (mandate_id, seq)`
  - `listings_by_sku (sku, ask_cents, vendor_id)`
  
  It is added to `REQUIRED_MIGRATIONS` and `lock.json`. **Writes need it applied first: migrate, then deploy.**
- **Catalog:** `GET /v1/catalog` and MCP `list_catalog` are keyset-paged: at most 100 a page, with `limit` (1–100), an opaque `after` cursor and `next`. A bad cursor or limit is `400 invalid`. `catalog()` still returns the first page, for existing callers. Oja reads `items` and is unaffected; it shows the first 100.
- **`GET /v1/audit/verify` is admin-only now** (AC-7.2). P1.12 adds signed checkpoints and incremental verify. `e2e.mjs`, `concurrency.mjs` and the harness send the admin token.
- **Smaller changes:**
  - `/health` adds `rate_limit: "binding+instance" | "instance"`, so P1.4b can confirm the binding is live on staging.
  - `concurrency.mjs` F2 now requires that its 429s are the anti-probing `rate_limited`, not the per-IP limit.
  - README Limits (AC-7.4), the regenerated error table, runbook and CLAUDE.md are updated.

## Open items (owner)

1. **Free-plan availability of the rate-limiting binding is undocumented.** P1.4b confirms it: `/health` on staging must say `rate_limit: "binding+instance"`. If `wrangler deploy` refuses `[[ratelimits]]`, the runbook says to stop rather than remove it; the choice is yours. Without the binding, the per-instance window still limits each IP, but only per instance.
2. **Limit values:** 100 requests per minute per IP. Oja's whole buy flow is about 10 calls. Carrier-grade NAT puts many users behind one address, so the limit is generous. Change it in both `IP_LIMIT_PER_60S` and the binding (a test keeps them in step).
3. **What this doesn't stop:** many addresses together (a botnet, IPv6 rotation) can still spend the daily quotas. Workers counts a request against the 100k before the arbiter runs. A global ceiling (a fixed key in the binding) is possible, but it would let one attacker lock everyone out. I haven't built it; it's in README Limits.
4. **Migration 0002 must be applied before this Worker is deployed** (`REQUIRED_MIGRATIONS`). Production migrations are manual and need your approval.
